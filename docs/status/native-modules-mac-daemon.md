The **macOS tamper model is now analysed in full** in `content-interception.md`, and the conclusions are load-bearing. (a) **A root `LaunchDaemon` is the macOS device-admin equivalent** — Android needed DeviceAdmin only because Android apps can never be root, and Android's *uninstall refusal* is OS-enforced rather than something the app does; macOS has no such API but supplies real privilege separation instead. (b) The structural break is that **macOS users have a terminal and Android users do not**, so guarding the Settings pane guards one door among many (`tccutil reset` was measured to run **without `sudo`**). (c) Therefore the design goal under the admin model is **"no bypass route that is both easy and silent"** — prevention is unreachable, but a route-by-route coverage table is satisfiable **entirely with signals needing zero permissions**: `csrutil status`, `dscl . -list /Users`, `dscl . -read /Groups/admin`, `kern.boottime`, all verified readable ungranted, plus `NSWorkspace.frontmostApplication` (bundle ID free; **window titles are redacted** — 0 of 21 exposed one without Screen Recording). Watch **outcomes, not routes**: one revocation poll catches both the Settings pane and `tccutil`. (d) **Text-layer command interception cannot work** — encoding is non-injective (`base64`/quoting/variable assembly), `eval` makes it halting-shaped, and the keyboard is one modality of many; the sound boundary is Endpoint Security's `AUTH_EXEC`, verified present, whose AUTH messages carry a **`deadline` past which the kernel kills your client**, making hash-keyed decision caching mandatory. (e) **A kext is strictly dominated by ES** — `KAuth` removed, MACF never public, signing cert harder to get than the ES entitlement, needs a local Recovery boot per machine; **zero third-party kexts** are loaded on the dev machine. (f) **SIP-off/`systemextensionsctl developer on` cannot ship**: with SIP off `TCC.db` is directly writable, a bigger hole than the one closed. (g) **Remote partner-held admin works** — Screen Sharing supplies the GUI session that admin prompts need (SSH cannot), so the partner need not be nearby; **FileVault pre-boot is the irreducible wall**, and Secure Token/bootstrap-token escrow gates remotely-created accounts. (h) Automating approval means a **root privileged helper, never a stored password**, and it **cannot grant TCC even as root**; an intent engine must **select among fixed enumerated operations and never generate a shell command**, or it is a confused deputy with root. Six findings. (1) **Inference cannot run on the calling thread** — `ScanLoop.tick` is driven by a main-run-loop `Timer`, the same thread AppKit draws on, and the real model measures **5.3 ms for one tile / 9.6 ms at 1024²** with a 1.54-aspect display frame costing three tiles; ~20 ms twice a second is a visible stutter in the interstitial being put up. `scan(_:)` therefore dispatches to a serial background queue and returns the last *completed* verdict, trading one cadence of latency, with `ClassificationDispatching` injected so tests stay synchronous. (2) **A tick with work in flight repeats the last verdict, never `.allow`** — the same load-bearing rule as the text path — and the in-flight guard is an atomic test-and-set so ticks cannot queue behind an inference slower than the cadence. (3) **`ImageOutcome.Allow` carries an optional score**: `None` = nothing classified, `Some(0.02)` = the model saw nothing, and collapsing them would make a silently broken image path look like a clean screen — precisely the failure session 6 spent a session on with `pixelFormat`. (4) **Whatever threshold is configured, its provenance does not extend to screen frames**, which are a different distribution with no measurement behind it; recorded in `docs/decisions/classifier-operating-point.md` rather than patched over, and the score is logged on every verdict so the margin is observable. (5) **No `warn` band on this path** — a probability has no warn range, and `ProtectionMode` is where a block legitimately becomes a warn. (6) **`regions` stays empty** — a 224-wide tile is not a located object. It forces the **`ScanLoop` two-scanner split** (one `Scanner` served both cadences before; the single-scanner init is kept for the scheduling tests), and the model now **ships sealed inside the signed bundle** (`AppBundle.assemble` gained `resources:`). Two smaller findings: **`Scanner` collides with `Foundation.Scanner`**, so a test double written unqualified subclasses the wrong one and fails at every call site; and both FFI targets declare the same rpaths, so every build emits a harmless `duplicate -rpath ignored`. 343 tests. Verified live with no TCC grant needed: `image-scan` loads the real model, reports threshold 0.465, and scores a 512² BGRA buffer at 0.266 in 6.9 ms; the signed bundle passes `codesign --verify --deep --strict` with **both** nested dylibs validated and runs the model with the build tree's `.ffi/lib` **moved away entirely**; appending one byte to the bundled model makes `codesign` report *"a sealed resource is missing or invalid"*, so a swapped model invalidates the bundle rather than silently disabling the path. **Outstanding: the classifier has never seen a real captured frame** — everything between `SCStream` and `ImageGuard` is exercised, but the two ends have only met through a synthetic buffer, and joining them needs the agent under `launchd` with a Screen Recording grant. **`ImageMapping.scanVerdict` now maps `ImageOutcome.warn` onto `.warn`** — the doc comment claiming a probability has no warn band was a real statement about the two-class model this daemon shipped with, and stopped being true once the classifier gained a `sexy` class (`packages/image-sandbox`'s `sandbox.rs`). `RealImageClassifier`'s constructor and `image-scan` CLI verb take `sexyThreshold`/`explicitThreshold` in place of one `threshold`; `HOLY_BLOCKER_IMAGE_SEXY_THRESHOLD` joins `HOLY_BLOCKER_IMAGE_THRESHOLD` as a second required env var for `agent`, and `LaunchdJob` gained `EnvironmentVariables` plist support (`launchctl setenv` was tried first and dropped — it does not reliably propagate to a job bootstrapped moments after the call) so `launchd-plist agent` can bake both thresholds into the installed job rather than depending on the generating shell's environment. 347 tests. **Run tests with `scripts/test.sh`, never bare `swift test`** — see `docs/components/mac-daemon/plan.md`

**Proxy blocklist wiring.** `ProxyBlocklist` resolves the signed list sealed in the bundle's `Resources/blocklist` into `--blocklist-dir`/`--blocklist-key` flags for `MitmProxyProcess`; `bundle` takes `[blocklist-dir] [blocklist-key-dir]` (`BLOCKLIST_DIR`/`BLOCKLIST_KEY_DIR` in `scripts/bundle.sh`). The daemon fails closed: `bundle` refuses to assemble without a list and `run` refuses to route traffic without one, unless `HOLY_BLOCKER_ALLOW_NO_BLOCKLIST=1` (development only). Observed through `URLSession` against a directly launched proxy and through the system proxy set by the root LaunchDaemon (403 over plain HTTP; the HTTPS refusal is a dropped connection). On Xcode 27 the release-profile `image_sandbox_ffi` dylib fails to link (`mis-aligned LINKEDIT string pool`); `PROFILE=debug ./scripts/build-ffi.sh` works around it.

**Release signing identity.** `Holy Blocker Release` is a second local certificate, made by `create-dev-signing-identity.sh --release`; `bundle` refuses to sign the release bundle with the development certificate, and `bundle-status` reports whether the two certificates are distinct (observed: distinct; a release bundle signed with the dev certificate was refused). Runbook: [signing-identity.md](../components/mac-daemon/signing-identity.md).

**Development bundle.** `HOLY_BLOCKER_BUNDLE_FLAVOR=development` makes `bundle` assemble `HolyBlockerDaemonDev.app` with identifier `com.holyblocker.daemon.dev` and name "Holy Blocker Dev". The state directory, launchd labels, install path and log names derive from the running bundle's identity, so the two builds share none of them, and the development flavor refuses any signing identity other than ad-hoc or `Holy Blocker Dev`. Both bundles were built and observed side by side with distinct identifiers. Separate TCC grants observed 2026-10-06 with `Holy Blocker Dev` signing, launching each bundle through `open` so the bundle is the responsible process: the release bundle reported all three permissions `granted` while the dev bundle reported `undetermined`. The owner then granted Accessibility to the dev bundle and confirmed the entry; a follow-up `permissions` run still read `undetermined` for the dev bundle, which is unexplained. **Development kill switch.** `dev-kill-switch` exists only in a binary compiled with `HOLY_BLOCKER_DEV_BUILD`, which `bundle.sh` sets for the development flavor and builds into `.build-dev`; a release build contains neither the verb nor the type (no match in `strings`, and the verb prints usage). It runs `launchctl bootout` on the running bundle's own agent and daemon labels only and refuses unless the running bundle is the development one, so a dev-compiled bare binary refuses too. A dev-compiled binary refuses to `bundle` as release. Observed 2026-10-06: from the development bundle it stopped a placeholder job under the dev agent label while a placeholder under the release agent label kept running. Not observed: the system-domain daemon target (nothing is installed, and booting it out needs root), and the real agent restoring proxy settings on that SIGTERM. The release-side signing refusal belongs to `mac-daemon.release-identity`.

**Tamper log** (`TamperLog`, `TamperLogStore`): fixed content-free code vocabulary, bounded and trimmed with a marker, session-start classification from uptime, `PermissionGate` events mapped to codes. Nothing writes to it yet; settings-guard, protection-schedule and the installer wire it in.
